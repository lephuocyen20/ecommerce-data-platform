# Plan: QA-fail manifest identity remediation and `NO_DATA` diagnosis

Status: **Workstream A implemented; QA PASS WITH WARNINGS. Workstream B read-only diagnosis complete: CONFIRMED expected no delta. Reader-path hardening remains separately dispositioned and is not part of this root-cause classification.**

## 1. Current Architecture

The relevant path is:

`PostgreSQL source -> incremental ingestion/watermark -> MinIO Bronze -> Spark Silver Parquet + completion manifest -> Airflow Silver verifier -> Gold dimensional reader`.

- `silver/incremental.py` produces the Silver completion manifest and currently
  computes `manifest_identity` from a payload excluding `manifest_identity` and
  `manifest_identities` to avoid a circular hash.
- `airflow/dags/pipeline_tasks/silver.py` verifies the persisted manifest and
  returns `manifest_identity` to downstream XCom consumers.
- `gold/implementation/dimensional/reader.py` re-reads and verifies the same
  manifest before Gold source resolution.
- `common/manifest.py` already owns shared JSON manifest primitives and is the
  narrowest shared home for one canonical identity helper.
- `ingestion/incremental/orchestrator.py` returns `NO_DATA` when extraction
  produces `row_count == 0`; the Airflow task maps this to a skipped validation
  result and no Silver artifact is created.

## 2. Problem or Requirement

### A. Canonical manifest identity

The latest QA-fail evidence records that persisted MinIO manifest identities do
not match Silver XCom identities for all committed tables. The code explains
the mismatch: the producer hashes the self-field-excluded payload, while the
Airflow verifier and Gold reader hash the full manifest JSON. This breaks the
cross-boundary content-addressed contract and blocks six-table certification.

Required remediation:

- Introduce one canonical manifest identity helper shared by the producer,
  Airflow verifier, and Gold reader.
- Preserve the existing non-circular identity semantics unless a new contract
  explicitly approves a format change: remove `manifest_identity` and
  `manifest_identities` before canonical JSON serialization, then SHA-256 the
  UTF-8 bytes with sorted keys, compact separators, and `ensure_ascii=False`.
- Use the helper for fresh publication, parent-orders references, Airflow XCom,
  and Gold read verification.

### B. `customers`/`products` `NO_DATA`

Recorded runtime evidence for the 2026-11-17 production Silver run says
`customers` and `products` returned `NO_DATA`; consequently neither table has a
manifest, schema, quality, or reconciliation artifact in that run. The current
code shows both tables use `updated_at` TIMESTAMP watermarks, and a zero-row
extract is converted to `status=NO_DATA` without creating a batch.

What is confirmed from repository/runtime records:

- The run was configured for the six-table selection and completed with four
  committed tables plus `NO_DATA` for `customers` and `products`.
- `TABLE_CONFIG` maps both tables to `(updated_at, TIMESTAMP)`.
- `execute_new_batch()` maps `prepare_pending_batch() is None` to
  `NO_DATA`; `prepare_pending_batch()` returns `None` when extraction has zero
  rows.
- `NO_DATA` is therefore not evidence of an exception or missing table by
  itself.

What remains unknown and must be diagnosed read-only before implementation or
rerun:

- effective PostgreSQL row counts and `MAX(updated_at)` for the two source
  tables;
- effective per-table watermark/checkpoint values at the run boundary;
- whether the source rows were older than the watermark, whether a replay
  window was active, and whether any source/config/runtime table selection
  mismatch existed;
- whether the runtime result was generated by a true zero-row extraction or by
  a recovery/selection branch.

No source-store query is authorized in this session. The diagnosis must report
these as unknown unless separately approved, sanitized, read-only evidence is
provided.

## 3. Proposed Solution

### Workstream A — identity helper

Add `canonical_manifest_identity(manifest)` to `common/manifest.py` with
fail-closed input validation. It should be deterministic and independent of
module-local private helpers. Replace the three boundary-local calculations:

1. Silver producer uses it for the published manifest and parent-orders
   reference.
2. Airflow verifier uses it for the XCom result after persisted-manifest
   metadata/inventory validation.
3. Gold reader uses it before comparing the identity recorded in lineage.

The helper must not mutate its input. Tests should prove key-order invariance,
exclusion of both identity fields, Unicode stability, and rejection of a
non-object input. A field mutation must change the identity.

### Workstream B — diagnosis only, then separately approved fix if needed

First produce a sanitized, read-only evidence table for `customers` and
`products` containing:

- exact selected-table config and runtime mode;
- source `COUNT(*)`, `MAX(updated_at)`, and optionally the next qualifying row
  under the exact incremental predicate;
- watermark `last_timestamp`, `last_id`, replay state, and relevant batch
  metadata, without exposing credentials or unrelated rows;
- the task result fields (`action`, `status`, `row_count`, `batch_id`) from the
  recorded runtime evidence.

Interpretation must distinguish:

- **expected no delta**: source rows exist but none qualify after the effective
  watermark/replay predicate;
- **state/config mismatch**: selected tables, source database, or watermark
  state do not match the intended run;
- **runtime extraction defect**: qualifying source rows exist but the extractor
  returned zero rows;
- **insufficient evidence**: no approved read-only source/checkpoint evidence.

Do not change watermark semantics, reset checkpoints, insert synthetic rows,
rerun the candidate, or allow Gold to reuse an old dimension as part of this
scope. Any behavior change for treating dimension `NO_DATA` as reusable state
is a separate design decision and requires a new approval.
